# 簡単にまとめると

取り扱いに関して注意が必要な文脈を、あるルールを満たす型にはめ込み
使用時はその文脈固有の取り扱いを意識せずに実装できる設計パターンです。

## もっとわかりやすく

「値」に付随する「文脈」の取り扱いを簡単にする仕組みです。

# モナドの例

* Result: 計算が失敗するかも知れない値
* Async: 結果が即座にわからない値
* Option: 結果が存在しないかも知れない値
* List: 複数の可能性を表す非決定的な値
    * ダイスの面が取りうる値の一覧など
    * ただし、登録済みユーザー一覧など、ただあるだけの値の並びは、List<User>型ではあるが**モナドではないように扱う**

# モナドであるためのルールとは

以下を満たす文脈付き値がモナドです。

1. fmapが定義できる
2. returnが定義できる
3. bind/joinが定義できる
4. モナド則を満たす

:::message
説明順の都合上、列挙していますが
厳密には1.は必須条件ではありません。
bindがあればfmapが導出可能なためです。
:::

# なんかfmapとかreturnとか出てきたけど何なの？

文脈付き値に対する抽象的な操作の概念です。
重要なものについて一つずつ記載します。
それぞれの操作には別名を持つものもありますが、割愛します。

## fmap

文脈の中身に関数を適用する操作

### 例


- 無いかも知れない値xに4を足す
- 即座にわからない値xに10をかける
- ダイスの面が取りうる値それぞれに2を足す


```fs
// Optionのfmap（F#ではOption.map）
Some 42 |> Option.map (fun x -> x * 2)  // Some 84
None    |> Option.map (fun x -> x * 2)  // None

// Listのfmap（List.map）
[1; 2; 3] |> List.map (fun x -> x * 2)  // [2; 4; 6]
```

## return

素の値を文脈に包む操作

### 例

- xを「無いかも知れない値x」として扱う
- xを「即座にわからない値x」として扱う

```fs
// OptionのReturn
Some 42      // int -> Option<int>

// ListのReturn
[42]         // int -> List<int>

// AsyncのReturn
async { return 42 }  // int -> Async<int>
```

## join

同じ文脈のネストをフラットな状態にする

### 例

- 「無いかも知れない「無いかも知れない値x」」 ->「無いかも知れない値x」
- 「即座にわからない「即座にわからない値x」」 ->「即座にわからない値x」

```fs
Some (Some 42) |> Option.flatten  // Some 42
[[1;2];[3;4]] |> List.concat      // [1;2;3;4]
```

## bind

あるモナドに、戻り値が同じモナド型になる関数を適用(fmap)してフラットにする(join)操作

実用上ではjoinよりbindのほうがよく使われます。

```fs
// Optionのbind
Some 42 |> Option.bind (fun x -> Some (x * 2))  // Some 84
None    |> Option.bind (fun x -> Some (x * 2))  // None

// Listのbind
[1; 2; 3] |> List.collect (fun x -> [x; x * 10])  // [1; 10; 2; 20; 3; 30]

// Asyncのbind
async {
    let! x = async { return 42 }        // Async<int>のAsyncを剥がしてxとしておく
    return x * 2
}  // Async<int> 84
```


# モナド則って？

以下の3つ

- 左単位元則
- 右単位元則
- 結合則

## 左単位元則

returnするだけなら即関数をbindしても、returnせずに関数を適用したのと同じであること。

```fs
// これらは等価
Some 42 |> Option.bind(fun x -> Some(x * 2))
42 |> (fun x -> Some(x * 2))
```

## 右単位元則

bind内のreturnは、値そのものに何も影響しないこと。

```fs
Some 42 |> Option.bind(fun x -> Some x) // Some 42
```

## 結合則

同じ文脈の入れ子は、どの順番で文脈を剥がしても結果が同じ。

```fs
// 左辺：fでbindしてからgでbind
(Some 42 |> Option.bind f) |> Option.bind g

// 右辺：fとgをまとめてbind
Some 42 |> Option.bind (fun x -> f x |> Option.bind g)
```


# モナド則満たさないとどうなるん？
モナド則を満たせないと、return join bindが元の値を保証できなかったり、bindのチェインの処理順に気を使わなければならなくなる

## 逆に言えば
モナド則を満たしていれば、同じ文脈に包む処理同士をbindでつなぐことで、処理内ではその文脈を気にしないでいられる

```fs
Some 42
|> Option.bind (fun x -> Some (x * 2))
|> Option.bind (fun x -> Some (x + 1))
|> Option.bind (fun x -> Some (x * 3))
// Some 126
```
もしくは
```fs
option {
    let! x = Some 42
    let! y = Some (x * 2)
    let! z = Some (y + 1)
    return z * 3
}
// Some 126
```
:::message
例えば`Some (x * 2)` を
「**`T`を渡して`Option<T>`が帰ってくる関数**(`T -> Option<T>`である何かしら)」
に置き換えてもこれらのチェインが成立します。
:::

# 「値」と「モナド(文脈付き値)」の境目ってなんぞ？

## 超雑に一言でまとめると

設計次第

## つまりどういうことやねん

何かを実装するにあたり、そもそもどんな文脈の取り扱いに注目が必要なのかを定めることが重要です。

比較的馴染みのある言語でモナドっぽい文脈付き値の取り扱いを見てみます。

### 例 JavaScript

JavaScript/TypeScriptを触ったことがある方なら、`async/await`という`Promise`型を簡単に扱う仕組みをご存知かと思います。

```JavaScript
async function getPosts() {
    const res = await fetch('/api/user/42') // 非同期処理の結果をresにbindし、後続の処理を実行
    const user = await res.json() // 非同期処理の結果をuserにbindし、後続の処理を実行
    const res2 = await fetch(`/api/posts/${user.id}`) // 以下同じく
    const posts = await res2.json()
    return posts
}
```

コレは「非同期」という文脈を簡単に取り扱うための構文です。
非同期関数の呼び出しに`await`とつけるだけで「非同期処理完了まで待機する」という「文脈の取り扱い」をインタプリタが受け持ってくれる仕組みです。

`async/await`が実装される前は、下記ほど何重にPromiseのチェーンを組むことは無いかと思いますが`then/catch/finally`を都度書いていて面倒だったかと思います。

```JavaScript:async/awaitを使わない場合
fetch('/api/user/42')
  .then(res => res.json())
  .then(user => fetch(`/api/posts/${user.id}`))
  .then(res => res.json())
  .then(posts => console.log(posts))
  .catch(err => console.error(err))
```

:::message
厳密にはPromiseはモナド則を満たしてはいません。
詳しくは割愛します。
:::

### 例 Rust

Rustではこのような例があります。

```Rust
fn find_user(id: u32) -> Result<User, Error> {
    let user = db.query(id)?;        // userにbindし、後続の処理を実行 Errなら文脈の処理として即return
    let valid = validate(user)?;     // 以下同じく
    let saved = save(valid)?;
    Ok(saved)
}
```

コレもjsの`async`と同様に
Result型という「失敗するかも知れない」文脈の処理を
`?`演算子で見た目上、簡潔にしています。
`?`演算子を使わない場合、下記のようにResultの文脈の処理を都度書き連ねる必要があります。

```Rust: ?を使わない場合
fn find_user(id: u32) -> Result<User, Error> {
    let user = match db.query(id) {
        Ok(u) => u,
        Err(e) => return Err(e),
    };
    let valid = match validate(user) {
        Ok(v) => v,
        Err(e) => return Err(e),
    };
    // ...
}
```

:::message
余談ですが、Rustにも`async/await`が存在します。
:::

### まとめると

このように「文脈」の処理を都度手動でコーディングすることは非常に面倒です。

モナドとは、これら「文脈」の取り扱いを共通規格にすることで、型として文脈の存在を明示しつつ
実装時は文脈の取り扱いそのものは意識しなくて済む仕組みなのです。

そのため、何をモナドとするかは、
**どんな文脈に注目する必要があるか次第**と言えます。

:::message
冒頭のモナドの例で、Listについて下記のように説明したのは
Listを「注目すべき文脈」として**扱わない**場合があるためです。
> ただあるだけの値の並びは、List<User>型ではあるが**モナドではないように扱う**

:::

# F#でのモナドの取り扱い例

モナドっぽいものを扱う仕組みとして「コンピュテーション式」があります。

```fsharp
// ビルダークラスの定義
type OptionBuilder() =
    member _.Return(x) = Some x           // return
    member _.Bind(opt, f) = match opt with // bind
                            | Some x -> f x
                            | None   -> None
    member _.ReturnFrom(opt) = opt         // return!

let option = OptionBuilder()

// 使用例 下記コンピュテーション式の型は Option<int>
option {
    let! x = Some 42          // let! が bind
    let! y = Some (x * 2)
    return y + 1               // return
}
```

:::message
コンピュテーション式のビルダークラスはモナド則を満たしていなくても実装可能です。
:::
